# Start a task

Use `agentflow` for everything below. Never create or edit files under `.agentflow/` by hand.

Run every `agentflow` command on its own, as a single command line. Never join commands with `&&`, `;` or `|`.

You never push, merge or open a pull request; that is the person's job.

1. Run `agentflow status`.
   - If it says there is no workspace, set one up from the project root (a git repository with `main` and `develop` branches). Run `agentflow init --workflow <path to this plugin's workflow.yaml>`.
     The file is `workflow.yaml` in the root of the dev-core plugin. In Claude Code that is `${CLAUDE_PLUGIN_ROOT}/workflow.yaml`; in Antigravity it is under `~/.gemini/antigravity-cli/plugins/dev-core/`. If the path is not filled in, search for a `dev-core/workflow.yaml` under `~/.claude/plugins` or that Antigravity folder.
   - If a task is already active, do not start another: use the continue skill, or ask the person whether to cancel it (`agentflow task cancel`).
2. Look at the roadmap with `agentflow roadmap list` (and the `next roadmap:` line of `agentflow status`): the task should serve one item, `R1`, `R2`, ... A short request is enough: "làm R2" (do R2) names the item, and "làm tiếp" (go on) means the item of the `next roadmap:` line; say which one you took. Ask the person which one when it is not obvious from the request; never pick for them. Read the item with `agentflow roadmap show <Rn>`: its documents are the request, so do not ask the person to describe the task or fill in a template. If the project has no roadmap, or the request fits no item, go on without one: `agentflow task new` only warns.
3. Take the title from the roadmap item when the task serves one (shorten it if needed). Otherwise ask the person for a short title. Then the type: `feature`, `bugfix` (both branch from `develop`), `hotfix` (from `main`), `refactor` (restructure code without changing what it does) or `chore` (upkeep that keeps the behaviour, such as a dependency upgrade; both from `develop`). Infer them from the request when it is obvious. For `refactor` and `chore` the test-spec step works the other way round: the tests must pass on the code as it is, and keep passing after the change. Also pick the size: `normal` (the default) or `small`, for a tiny, well-bounded change that fits in at most 3 plan items. A small task skips the approval of the plan (confirm and review still need the person) and its security step runs only Gitleaks and Semgrep. Use `small` only when the person asks for it or the request is clearly that small; when in doubt use `normal`. A `hotfix` gets the size `hotfix` by itself (do not pass `--size`): no approval of the plan, at most 3 plan items, every scan; confirm, test-spec and review still need the person, and when it is done agentflow prints the commands the person runs to merge it into `main` and back into `develop`. Do not ask for a roadmap item for a hotfix.
4. The working tree must be clean. If `agentflow` says it is not, show the person what is uncommitted and ask what to do; do not discard anything.
5. Run `agentflow task new "<title>" --type <type> --roadmap <Rn>` (add `--size small` for a small task; leave `--roadmap` out only when no item fits). **The branch the task starts from** is the project's choice (`git.base.*` settings, else develop; main for a hotfix): do not pass `--base` unless the person names a branch ("tách từ feature/login", "branch off release/2"), then add `--base <that branch>` exactly as they wrote it. Never pick a base yourself. The command prints `created on branch <task branch> from <base>`: say it aloud, and if it warns that the base is behind origin, tell the person and stop before going on, so they can `git pull` first (cancel the task with `agentflow task cancel` if they want to start over). The item moves to `doing`; finishing the task never closes it, a person does (`agentflow roadmap set Rn done`). Read the warnings it prints aloud to the person: an unconfirmed mission or roadmap item is theirs to confirm, not yours. It creates the branch `<type>/T-001-<slug>` and switches to it. If it says the previous task has no approval tag, tell the person: they run `agentflow task seal <id>` themselves. If it warns that the previous task was never replanned, or that its replan is only proposed, tell the person and offer the replan skill (`replan`); they close it with `agentflow replan done` or `agentflow replan skip` themselves.
6. Carry on with the continue skill. It runs the **confirm** step with the orchestrator agent and stops at the person's approval; after the approval it keeps going by itself. The cycle is confirm, plan, **test-spec** (the tester writes the tests first and agentflow checks that they fail; a person approves, small task or not), implement, test, security, review.
